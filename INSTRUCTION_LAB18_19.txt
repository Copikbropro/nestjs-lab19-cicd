1. СТРУКТУРА ПРОЕКТА И РЕАЛИЗАЦИЯ ЗАДАНИЙ
================================================================================
Проект объединяет код приложения из ЛР №17 (NestJS + PostgreSQL + JWT + RBAC)
и дополняет его всеми артефактами для ЛР №18 и ЛР №19:

По Лабораторной работе №18:
- Dockerfile.basic       -> Задание 1: базовый одноступенчатый Dockerfile.
- Dockerfile             -> Задание 2: оптимизированный многоступенчатый
                            Dockerfile (этапы builder и production с удалением
                            devDependencies через npm prune --omit=dev).
- docker-compose.yml     -> Задание 3: запуск двух связанных контейнеров:
                            1) lab18_postgres (база данных PostgreSQL 16)
                            2) lab18_nestjs_api (NestJS API из multi-stage образа)
- .env и .env.example    -> Переменные окружения для подключения к БД и JWT.
- .gitignore             -> Исключает .env, node_modules, dist из Git.

По Лабораторной работе №19:
- src/main.ts            -> Задание 1: динамический порт process.env.PORT || 3000
                            и прослушивание интерфейса '0.0.0.0' для облака.
- Procfile               -> Задание 1: команда запуска для облачных PaaS
                            (web: npm run start:prod).
- package.json           -> Задание 1: скрипты build, start:prod, test и engines.
- .github/workflows/deploy.yml -> Задания 2 и 3: автоматический CI/CD пайплайн
                            GitHub Actions (checkout -> setup-node -> npm install
                            -> npm run test -> npm run build -> docker build ->
                            docker push -> деплой в облако Heroku).
- src/app.controller.spec.ts и src/auth/auth.service.spec.ts -> Юнит-тесты Jest,
                            которые запускаются в CI перед сборкой образа.

2. ВЫПОЛНЕНИЕ ЛР №18 (ЗАДАНИЯ 1 И 2): СРАВНЕНИЕ РАЗМЕРОВ DOCKER-ОБРАЗОВ
================================================================================
Откройте терминал в корне распакованной папки проекта (где лежат Dockerfile
и Dockerfile.basic) и выполните следующие команды для демонстрации преподавателю:

Шаг 1. Соберите базовый одноступенчатый образ (Задание 1):
       docker build -f Dockerfile.basic -t nestjs-lab18:basic .

Шаг 2. Соберите оптимизированный многоступенчатый образ (Задание 2):
       docker build -f Dockerfile -t nestjs-lab18:optimized .

Шаг 3. Сравните размеры обоих образов командой:
       docker images nestjs-lab18

       Что вы увидите:
       - nestjs-lab18:basic     ~ 350–420 МБ (содержит исходники src/, кэш npm,
                                компиляторы python3/make/g++ и все devDependencies:
                                typescript, @nestjs/cli, jest, ts-jest).
       - nestjs-lab18:optimized ~ 160–210 МБ (содержит только скомпилированную
                                папку dist/ и production-зависимости).
       Экономия размера образа составляет ~50% (в 2 раза меньше)!

3. ВЫПОЛНЕНИЕ ЛР №18 (ЗАДАНИЕ 3): ЗАПУСК ЧЕРЕЗ DOCKER COMPOSE
================================================================================
Шаг 1. Убедитесь, что в корне проекта есть файл .env (он уже создан в архиве).
Шаг 2. Запустите оба контейнера (NestJS API + PostgreSQL) одной командой:

       docker compose up --build

       (Для запуска в фоновом режиме добавьте -d: docker compose up --build -d)

Шаг 3. Дождитесь вывода в консоли:
       - lab18_postgres: "database system is ready to accept connections" (healthy)
       - lab18_nestjs_api: "Application is running on: http://0.0.0.0:3000"

Шаг 4. Проверить работающие контейнеры можно командой:
       docker compose ps

Остановить и удалить контейнеры:        docker compose down
Остановить и очистить том базы данных:  docker compose down -v

4. ПРОВЕРКА РАБОТЫ ПРИЛОЖЕНИЯ В POSTMAN (ПОШАГОВО)
================================================================================
Вы можете либо импортировать файлы из папки postman/:
  - postman/Lab18_19_Docker_CICD.postman_collection.json
  - postman/Lab18_19_Docker.postman_environment.json
либо отправлять запросы вручную по шагам ниже:

Шаг 1. Проверка статуса приложения и динамического порта (ЛР №19 Задание 1):
  - Метод: GET
  - URL:   http://localhost:3000/
  - Ответ (200 OK):
    {
      "application": "NestJS Lab 17-19 (Auth, Docker Multi-Stage, CI/CD)",
      "status": "running",
      "environment": "production",
      "port": 3000
    }

Шаг 2. Проверка Health-Check эндпоинта контейнера:
  - Метод: GET
  - URL:   http://localhost:3000/health
  - Ответ (200 OK): {"status": "ok", "uptime": ..., "timestamp": "..."}

Шаг 3. Регистрация пользователя (проверка связи контейнера API с контейнером БД):
  - Метод: POST
  - URL:   http://localhost:3000/auth/register
  - Body -> raw -> JSON:
    {
      "email": "student@psu.by",
      "username": "student",
      "password": "password123"
    }
  - Ответ (201 Created): пользователь сохранен в контейнер PostgreSQL!

Шаг 4. Логин и получение JWT-токена:
  - Метод: POST
  - URL:   http://localhost:3000/auth/login
  - Body -> raw -> JSON:
    {
      "username": "student",
      "password": "password123"
    }
  - Скопируйте значение поля "access_token" из ответа (без кавычек).

Шаг 5. Создание задачи в БД (проверка защищенного маршрута):
  - Метод: POST
  - URL:   http://localhost:3000/tasks
  - Authorization -> Type: Bearer Token -> вставьте скопированный токен.
  - Body -> raw -> JSON:
    {
      "title": "Сдать ЛР №18 и №19",
      "description": "Docker Compose и CI/CD настроены"
    }
  - Ответ (201 Created): задача сохранена в PostgreSQL.

Шаг 6. Получение списка задач:
  - Метод: GET
  - URL:   http://localhost:3000/tasks
  - Authorization -> Bearer Token -> тот же токен.
  - Ответ (200 OK): массив с созданной задачей.

5. ВЫПОЛНЕНИЕ ЛР №19: ПРОВЕРКА ТЕСТОВ И НАСТРОЙКА GITHUB ACTIONS CI/CD
================================================================================
Шаг 1. Локальный запуск автотестов (Задание 3 ЛР №19):
       Выполните в терминале:
       npm install
       npm run test

       Запустится Jest и выполнит тесты из src/app.controller.spec.ts и
       src/auth/auth.service.spec.ts (все тесты пройдут с результатом PASS).

Шаг 2. Загрузка проекта в GitHub:
       1) Создайте новый репозиторий на GitHub (например, nestjs-lab19-cicd).
       2) В папке проекта выполните:
          git init
          git add .
          git commit -m "Lab 18-19: Docker multi-stage, Compose and CI/CD pipeline"
          git branch -M main
          git remote add origin https://github.com/<ВАШ_ЛОГИН>/nestjs-lab19-cicd.git
          git push -u origin main

Шаг 3. Настройка секретов (Secrets) в репозитории GitHub:
       Перейдите в репозиторий на GitHub -> Settings -> Secrets and variables ->
       Actions -> кнопка "New repository secret" и добавьте секреты:
       - DOCKERHUB_USERNAME  — ваш логин на hub.docker.com
       - DOCKERHUB_TOKEN     — токен доступа из Docker Hub (Account Settings -> Security)
       - HEROKU_API_KEY      — API-ключ из настроек аккаунта Heroku (если деплоите в Heroku)
       - HEROKU_APP_NAME     — имя вашего приложения в Heroku

       Примечание: даже если секреты Docker Hub/Heroku еще не заполнены, при push
       в ветку main пайплайн .github/workflows/deploy.yml все равно запустится,
       выполнит checkout, установку зависимостей, юнит-тесты (npm run test),
       сборку NestJS (npm run build) и локальную сборку Docker-образа!

Шаг 4. Просмотр работы пайплайна:
       Откройте вкладку "Actions" в вашем репозитории на GitHub — вы увидите
       выполнение всех шагов workflow "CI/CD Pipeline — Test, Build, Docker & Cloud Deploy".

6. ПОЧЕМУ ШАГ ТЕСТИРОВАНИЯ ПЕРЕД СБОРКОЙ КРИТИЧЕСКИ ВАЖЕН ДЛЯ CI
   (ОТВЕТ К ЗАДАНИЮ 3 ЛАБОРАТОРНОЙ РАБОТЫ №19)
================================================================================
В файле .github/workflows/deploy.yml шаг запуска тестов (`npm run test`)
расположен строго ПОСЛЕ установки зависимостей (`npm install`), но ДО сборки
приложения (`npm run build`), сборки Docker-образа и деплоя в облако.

Почему это критически важно для методологии Continuous Integration (CI):
1) Принцип «Fail Fast» (быстрое обнаружение ошибок): если разработчик внес
   ошибку в бизнес-логику (например, сломал хеширование паролей или генерацию
   JWT), пайплайн остановится на этапе тестирования за несколько секунд, не
   тратя вычислительные ресурсы и время на сборку тяжелого Docker-образа и его
   отправку в реестр.
2) Защита продакшн-среды (Quality Gate): сломанный или нестабильный код
   гарантированно не попадет в контейнерный реестр и не перезапишет работающую
   версию приложения в облаке (Heroku / Cloud Run), что исключает простой
   сервиса для конечных пользователей.
3) Как реализована остановка пайплайна при ошибке: в GitHub Actions каждый шаг
   выполняется в оболочке bash с проверкой кода возврата (exit code). Если хотя
   бы один тест Jest не пройден, команда `npm run test` возвращает код ошибки 1,
   GitHub Actions помечает шаг красным крестиком (Failed) и немедленно прерывает
   выполнение всех последующих шагов (сборки и деплоя).
