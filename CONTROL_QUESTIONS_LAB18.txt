ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ К ЛАБОРАТОРНОЙ РАБОТЕ №18
«Настройка окружения и деплой приложения в Docker»
================================================================================

1. В чем заключаются основные преимущества использования Docker по сравнению
   с традиционной виртуализацией?
--------------------------------------------------------------------------------
- Легковесность и малый размер: контейнеры не включают в себя полноценную
  гостевую операционную систему (как виртуальные машины), а используют ядро
  хостовой ОС. Благодаря этому образ весит десятки/сотни мегабайт вместо
  десятков гигабайт.
- Мгновенный запуск: контейнер запускается за доли секунды (как обычный процесс),
  тогда как загрузка виртуальной машины занимает минуты.
- Высокая плотность и экономия ресурсов: на одном сервере можно запустить в разы
  больше контейнеров, чем ВМ, так как нет накладных расходов на гипервизор и
  эмуляцию оборудования.
- Переносимость и воспроизводимость среды: контейнер содержит код и все его
  зависимости, что полностью решает проблему «на моей машине всё работает».


2. Опишите назначение ключевых инструкций Dockerfile: FROM, WORKDIR, COPY, RUN, CMD.
--------------------------------------------------------------------------------
- FROM — задает базовый образ, на основе которого строится новый образ
  (например, FROM node:20-alpine). Всегда является первой инструкцией сборки.
- WORKDIR — устанавливает рабочую директорию внутри контейнера для всех
  последующих инструкций (RUN, COPY, CMD). Если папка не существует, она
  создается автоматически.
- COPY — копирует файлы и директории с локальной машины (контекста сборки)
  внутрь файловой системы контейнера (например, COPY package*.json ./).
- RUN — выполняет команды внутри контейнера на этапе сборки образа и фиксирует
  результат в новом слое (например, RUN npm install или RUN npm run build).
- CMD — задает команду по умолчанию, которая будет выполнена при запуске
  контейнера из собранного образа (например, CMD ["node", "dist/main.js"]).


3. Для чего нужна многоступенчатая сборка (multistage build), и как она
   помогает оптимизировать Docker-образы?
--------------------------------------------------------------------------------
Многоступенчатая сборка (multistage build) позволяет использовать в одном
Dockerfile несколько инструкций FROM, разделяя процесс на этап сборки (builder)
и финальный рабочий этап (production).
- На этапе builder устанавливаются все инструменты разработки и компиляции
  (typescript, @nestjs/cli, компиляторы C++), после чего исходный код TypeScript
  компилируется в JavaScript (папка dist/).
- На этапе production берется чистый базовый образ, в который с помощью
  `COPY --from=builder` переносятся ТОЛЬКО готовая папка `dist/` и очищенные
  от devDependencies зависимости `node_modules/`.
- В результате из итогового образа удаляются исходники, кэш и сборочные
  инструменты, что уменьшает размер образа в 2–4 раза, ускоряет его загрузку
  по сети и снижает поверхность атаки (повышает безопасность).


4. Что такое Docker Compose, и в каких случаях он используется?
--------------------------------------------------------------------------------
Docker Compose — это инструмент для описания, запуска и управления
многоконтейнерными приложениями с помощью декларативного YAML-файла
(docker-compose.yml).
Он используется в случаях, когда приложение состоит из нескольких связанных
сервисов (например, backend на NestJS + база данных PostgreSQL + кэш Redis).
Одной командой `docker compose up` инструмент автоматически создает общую
изолированную сеть, тома для хранения данных (volumes), задает порядок запуска
(depends_on) и передает переменные окружения всем контейнерам.


5. Как в NestJS-приложении обрабатываются переменные окружения, и почему
   это важно при контейнеризации?
--------------------------------------------------------------------------------
В NestJS для работы с переменными окружения используется официальный пакет
`@nestjs/config` (модуль `ConfigModule.forRoot()` и сервис `ConfigService`),
который считывает значения из системных переменных ОС (`process.env`) или из
файла `.env`.
При контейнеризации это критически важно, так как один и тот же неизменяемый
Docker-образ должен работать в разных средах (локально, на тестовом сервере,
в продакшене). Вместо пересборки образа мы просто передаем разные параметры
подключения к БД (DB_HOST, DB_PASSWORD), порт (PORT) и секреты (JWT_SECRET)
через переменные окружения контейнера.


6. Объясните, почему файлы .env никогда не следует добавлять в систему
   контроля версий (например, Git).
--------------------------------------------------------------------------------
Файл `.env` содержит конфиденциальные данные: пароли от баз данных, секретные
ключи подписи JWT, API-ключи сторонних сервисов и облачных платформ.
Если добавить `.env` в Git:
1) Любой, кто получит доступ к репозиторию (или если репозиторий станет
   публичным), сможет украсть учетные данные и скомпрометировать систему.
2) Даже если удалить `.env` в следующем коммите, он навсегда останется в истории
   изменений Git.
3) У каждого разработчика и сервера свои локальные настройки (разные порты и
   пароли), поэтому в репозиторий добавляют только шаблон `.env.example` без
   реальных секретов, а сам `.env` вносят в `.gitignore`.
