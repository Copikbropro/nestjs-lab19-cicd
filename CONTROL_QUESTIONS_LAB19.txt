ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ К ЛАБОРАТОРНОЙ РАБОТЕ №19
«Развертывание приложения в облаке и настройка CI/CD»
================================================================================

1. Объясните основные принципы и преимущества CI/CD.
--------------------------------------------------------------------------------
CI/CD (Continuous Integration / Continuous Delivery & Deployment) — это
методология DevOps, основанная на автоматизации всех этапов доставки кода от
коммита разработчика до работы в продакшене.

Основные принципы:
- Частая интеграция небольших изменений в общую ветку репозитория.
- Полная автоматизация сборки, тестирования и развертывания (pipeline as code).
- Единый источник истины (все конфигурации пайплайнов и инфраструктуры хранятся
  в репозитории).
- Быстрая обратная связь (fail fast): немедленное уведомление команды при
  провале сборки или тестов.

Преимущества:
- Раннее выявление багов и конфликтов слияния, когда их исправление стоит
  минимальных усилий.
- Исключение человеческого фактора и рутинных ошибок при ручном деплое.
- Ускорение вывода новых функций (time-to-market) и предсказуемость релизов.


2. В чем разница между непрерывной интеграцией, непрерывной доставкой и
   непрерывным развертыванием?
--------------------------------------------------------------------------------
- Непрерывная интеграция (Continuous Integration, CI) — автоматическая сборка
  проекта и прогон автотестов при каждом изменении кода (push / pull request)
  для проверки его работоспособности.
- Непрерывная доставка (Continuous Delivery, CD) — следующий этап после CI:
  успешно протестированный код автоматически собирается в готовый релизный
  артефакт (например, Docker-образ) и готов к выкладке, но сам запуск деплоя
  в продакшн требует ручного подтверждения ответственного специалиста.
- Непрерывное развертывание (Continuous Deployment, CD) — полная автоматизация
  без участия человека: каждое изменение, прошедшее все этапы CI и тесты,
  автоматически разворачивается в продакшн-среде.


3. Опишите роль GitHub Actions в процессе CI/CD. Каковы ключевые компоненты
   файла workflow.yml?
--------------------------------------------------------------------------------
GitHub Actions — это встроенная в GitHub платформа автоматизации, которая
позволяет запускать CI/CD-конвейеры непосредственно при событиях в репозитории.

Ключевые компоненты файла workflow (например, .github/workflows/deploy.yml):
- name — человекочитаемое название рабочего процесса (workflow).
- on — триггеры (события), запускающие пайплайн (например, push в ветку main,
  pull_request или ручной запуск workflow_dispatch).
- jobs — набор заданий (например, build-test-and-deploy), которые выполняются
  на виртуальных машинах-раннерах (`runs-on: ubuntu-latest`).
- steps — последовательность конкретных шагов внутри job: использование
  готовых экшенов (`uses: actions/checkout@v4`) или выполнение консольных команд
  (`run: npm run test`).
- env / secrets — передача переменных окружения и зашифрованных секретов.


4. Как следует подготавливать NestJS-приложение к развертыванию в облачной
   среде? Какие параметры необходимо учитывать (например, порт, Procfile)?
--------------------------------------------------------------------------------
Для корректной работы в облачных PaaS- и контейнерных платформах (Heroku,
Google Cloud Run, Render) необходимо учесть следующие параметры:
1) Динамический порт: облачный провайдер сам назначает порт и передает его через
   переменную окружения `PORT`. В `src/main.ts` нужно использовать
   `process.env.PORT || 3000` и слушать адрес `'0.0.0.0'` (а не только localhost).
2) Файл Procfile: для PaaS-платформ (таких как Heroku) в корень проекта
   добавляется файл `Procfile` со строкой `web: npm run start:prod`, указывающей
   платформе, какой процесс запускать для приема HTTP-трафика.
3) Скрипты в package.json: должны быть настроены скрипты `"build": "nest build"`
   и `"start:prod": "node dist/main.js"`, а также указана версия Node.js в поле
   `"engines"`.
4) Конфигурация через переменные окружения: параметры подключения к облачной БД
   (например, `DATABASE_URL` с поддержкой SSL) и секреты должны считываться из
   переменных окружения.


5. Объясните, почему важно использовать "секреты" (secrets) в пайплайнах CI/CD.
--------------------------------------------------------------------------------
Для автоматической отправки образов в Docker Hub и деплоя в облако пайплайну
требуются логины, пароли, токены доступа и API-ключи. Хранить их в открытом
виде в YAML-файле пайплайна или в коде репозитория категорически запрещено, так
как любой человек с доступом к репозиторию или логам сборки сможет их украсть.

Механизм Secrets в GitHub Actions решает эту проблему:
- Значения секретов хранятся в зашифрованном виде на серверах GitHub и доступны
  только во время выполнения пайплайна через контекст `${{ secrets.NAME }}`.
- GitHub автоматически маскирует (скрывает символами `***`) значения секретов
  в логах выполнения пайплайна, предотвращая их случайную утечку.
